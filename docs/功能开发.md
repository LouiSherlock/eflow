# Tauri 2 开发 Android 电子书应用：完整方案

## 先说结论

方案可行。阅读器的核心（EPUB/MOBI 排版渲染）本来就是 Web 技术，正好由 Tauri 的 WebView 承载。Rust 负责本地数据和重计算，Android 原生能力靠自写 Kotlin 插件补，Tauri 插件可以直接用 Kotlin/Java 调用 Android API。

主要风险有两个：

- 系统 WebView 版本碎片化。
- 原生集成（SAF、TTS、音量键、后台服务）的工作量。

如果只做 Android，并且重度依赖 PDF 和后台朗读，原生 Kotlin + Readium 更稳。如果想和桌面端共用一套代码，Tauri 是合理选择。

## 1. 总体架构

```
Android App（单 Activity）
├─ WebView（系统 WebView / Chromium）
│   └─ React SPA（Vite）
│       ├─ 书架 / 设置 / 批注列表 UI
│       ├─ 阅读器容器 → foliate-js <foliate-view>（每章一个沙箱 iframe）
│       └─ Zustand 状态
│            │ invoke / events          │ fetch book://（支持 Range）
├─ Rust Core（Tauri）
│   ├─ commands：书库 / 进度 / 批注 / 设置
│   ├─ SQLite（+FTS5）、导入管线、TXT 解码分章
│   ├─ 自定义协议 book://、同步（WebDAV）
│            │ JNI（Tauri 插件桥）
└─ Kotlin 插件
    ├─ SAF 选书 / 选目录、"用本应用打开"Intent
    ├─ TTS + 前台服务 + MediaSession
    └─ 音量键、亮度、常亮、沉浸模式、刘海/导航栏 insets
```

**职责划分原则：**

- 书籍解析和渲染只用一套引擎（foliate-js），避免 JS 和 Rust 两套解析器行为不一致。
- 文件、数据库、索引、网络、重计算放 Rust。
- 系统能力放 Kotlin。

## 2. 技术栈

| 层 | 选型 | 说明 |
|---|---|---|
| 前端框架 | Vite + React 19 + TypeScript（SPA） | 不用 Next.js，Tauri 里只能静态导出，没有收益 |
| 路由 | React Router（memory/hash 模式） | 要接管 Android 返回键 |
| 状态 | Zustand | 阅读页的高频事件（relocate）不要驱动整棵树重渲染 |
| 样式 | Tailwind + 自定义 CSS 变量主题 | 见难点 1，Tailwind v4 对 WebView 版本有要求 |
| 阅读引擎 | foliate-js | 见下方说明 |
| 解压 | zip.js（+ fflate） | foliate-js 自身不带解压库 |
| PDF（二期） | PDF.js | 走 foliate-js 的固定布局适配 |
| Rust 核心 | Tauri 2.x、rusqlite 或 sqlx、tokio、serde、tracing | |
| Rust 工具库 | encoding_rs + chardetng（TXT 编码）、blake3（去重）、image（封面缩略图）、reqwest（用 rustls） | |
| 原生 | Kotlin 插件；NDK r28+；minSdk 以 Tauri 模板默认为起点 | |

**关于 foliate-js**：

- 它支持 EPUB、MOBI、KF8(AZW3)、FB2、CBZ，PDF 仅为实验性且依赖 PDF.js。
- 项目自己声明 API 不稳定，随时可能变动，所以要以 git submodule 方式引入并锁定版本。
- 分页器沿用 epub.js 的 CSS 多列方案，因此速度偏慢，部分 CSS 表现也可能异常。
- 同一份说明里还提到固定布局渲染器尚不完善，需要实测。
- 备选是 Readium 的 TS 导航器。它更工程化，但接入成本更高。

## 3. 核心模块设计

**3.1 导入管线**

1. Kotlin 用 `ACTION_OPEN_DOCUMENT`（多选）选书，或用 `OPEN_DOCUMENT_TREE` 选目录并持久化授权。
2. 立刻用 ContentResolver 流式复制到应用私有目录，边复制边算 blake3，并通过事件上报进度。
3. 按 hash 去重后入库。
4. 前端用 foliate-js 解析元数据，并用 canvas 生成封面（webp），再把字节交给 Rust 存盘。

导入队列并发数设 1–2，防止低端机内存爆掉。

**3.2 书籍访问：`book://` 自定义协议**

foliate-js 配 zip.js 可以对 File 或 URL 做随机读取。zip.js 被推荐的原因，是它对 File 对象和 HTTP Range 请求都支持随机访问。所以让 Rust 提供支持 Range 的协议，前端 `fetch` 即可按需读取，不用把整本书读进 JS 堆。

```rust
tauri::Builder::default()
  .register_asynchronous_uri_scheme_protocol("book", |ctx, req, responder| {
      let app = ctx.app_handle().clone();
      tauri::async_runtime::spawn(async move {
          // 1. 从 req.uri().path() 取 book_id（只取 id，绝不取路径，防目录穿越）
          // 2. 查库得到私有目录下的真实文件路径
          // 3. 解析 Range 头，seek 读取对应字节段
          // 4. 返回 206 + Content-Range + Accept-Ranges: bytes
          // 5. 加 Access-Control-Allow-Origin: *（App 源与协议源不同）
          responder.respond(serve_book(&app, req).await);
      });
  })
```

Android 上自定义协议的 URL 形如 `http://book.localhost/<id>`，具体以实测为准。

**3.3 位置与进度模型**

- EPUB 存 CFI + 百分比，不要存页码，因为字号一变页码就失效。
- TXT 存字符偏移，PDF 存页码 + 页内偏移。
- 写进度做防抖（约 1–2 秒），并在 `visibilitychange` 和原生 `onPause` 时强制落盘。

**3.4 批注**

用 foliate-js 的 overlayer 渲染高亮，数据库存 `cfi_range + 原文片段 + 颜色 + 笔记`。章节 iframe 每次加载后，要重新绘制该章节的高亮。

**3.5 搜索**

- 书内搜索：foliate-js 的 search 模块。
- 全库全文检索：SQLite FTS5。中文分词可以用 trigram tokenizer，或导入时用 jieba 预分词。需要确认所用 SQLite 构建启用了 FTS5。

**3.6 同步**

先做 WebDAV，坚果云、Alist 之类的用户很多。同步内容是进度、批注和书签，不同步书籍本体。每条记录带 `updated_at + device_id`，用 last-write-wins；删除用软删除标记，否则会被"复活"。

**3.7 朗读（TTS）**

由 Kotlin 调 Android `TextToSpeech`，加前台服务和 MediaSession。前端只负责把"当前章节文本分句"喂给原生，并接收"朗读到第几句"的事件来高亮。

**3.8 数据模型（SQLite）**

```
books(id, hash, format, title, author, lang, path, cover_path, size, added_at)
progress(book_id, cfi, percent, updated_at, device_id)
annotations(id, book_id, cfi_range, text, note, color, created_at, updated_at, deleted)
bookmarks(id, book_id, cfi, label, created_at, deleted)
shelves / book_shelf        -- 分组、标签
reading_sessions(book_id, start, end)   -- 阅读统计
settings(key, value)
```


## 5. 难点（按风险排序）

1. **系统 WebView 版本碎片化**：无 GMS 的国产 ROM 和老机型，WebView 可能很旧。Tailwind v4 需要较新的 Chromium（大约 111+），不满足会直接样式错乱。对策是先确定最低支持的 WebView 版本，启动时解析 UA 检测，过低就提示升级。如果必须兼容更老的设备，用 Tailwind v3 + autoprefixer，并设置合适的构建 target。
2. **Android 文件访问（SAF / content://）**：`dialog` 插件在 Android 上返回 content URI，`fs` 插件对它的支持程度要实测。最稳的做法是自己写 Kotlin 插件，用 ContentResolver 读流并复制到私有目录。社区也有封装 SAF 的插件，可以评估，但要确认维护状态。
3. **分页性能与准确性**：网络小说转成的 EPUB 常有单章几 MB 的 HTML，CSS 多列分页会卡。对策是限制样式变更频率（字号滑动要防抖）、预处理超大章节，并在低端机上实测。
4. **iframe 内的手势和选区**：触摸和选区事件发生在章节 iframe 里，不会冒泡到外层。要在章节加载事件里给每个 iframe 文档单独挂监听。Android 原生的文字选择菜单难以定制，通常要用 `selectionchange` 自绘选择工具栏，并处理好"长按选词"和"点击翻页"的冲突。
5. **生命周期与状态丢失**：Activity 可能被系统回收，WebView 重建后 JS 状态全丢。所以进度、设置、当前打开的书都必须持久化，启动时能恢复到上次的阅读位置。
6. **TTS 与后台播放**：Web Speech API 在 Android WebView 里不可靠，要走原生。后台朗读需要前台服务，Android 14+ 还要在 Manifest 声明前台服务类型（mediaPlayback）和对应权限，Android 13+ 要申请通知权限。
7. **中文场景**：
   - TXT 编码识别（UTF-8/GBK/GB18030）。
   - 用正则按"第X章"切分章节，并允许用户自定义规则。
   - 繁简转换（OpenCC）。
   - 竖排、ruby、标点挤压。
   TXT 对国内用户往往是第一刚需，别只做 EPUB。
8. **边到边显示与系统栏**：targetSdk 35 起强制 edge-to-edge，刘海、导航栏、沉浸模式都要处理。CSS 的 `env(safe-area-inset-*)` 在 WebView 里表现不一致，更稳的做法是让 Kotlin 把 insets 传给前端。
9. **音量键翻页**：必须改 `MainActivity` 拦截按键，再通过 `evaluateJavascript` 或插件事件通知前端。这也是 `gen/android` 要提交进版本库的原因。
10. **构建与发布**：
    - Rust 要装 `aarch64`、`armv7`、`x86_64`（模拟器）等 Android target。
    - 用 `--split-per-abi` 或只发 arm64 来控制体积。
    - Google Play 对原生库的 16KB 页大小有要求，NDK r28+ 默认满足，具体以官方文档为准。
    - 签名密钥妥善备份，建议用 Play App Signing。
    - 国内分发不走 Play，需要自行处理各应用商店的上架要求。

## 6. 注意事项

- **版本锁定**：`tauri` crate、`@tauri-apps/api` 和各官方插件保持同一批次版本，升级时一起升。
- **提交 `src-tauri/gen/android`**：忽略构建产物和 `local.properties`，其余提交。
- **最小权限**：capabilities 不开放宽泛的 fs scope。书籍文件只由 Rust 读写，前端不直接碰文件系统。
- **安全**：foliate-js 明确要求配置 CSP，屏蔽除 self 之外的所有脚本。EPUB 里的脚本一律不执行，章节 iframe 保持 sandbox。
- **私有存储即卸载即删**：必须提供"导出备份 / 导入"（进度、批注、书签的 JSON），并考虑 Android Auto Backup 的策略。
- **返回键**：自己接管，阅读页返回书架、书架再返回才退出（可用 `@tauri-apps/api/app` 的 `onBackButtonPress`）。
- **开发调试**：真机调试时 Vite 要监听 `TAURI_DEV_HOST`；WebView 用 `chrome://inspect` 调试。
- **日志**：用 tracing 写本地日志文件，加 panic hook，方便用户反馈问题。
- **WebView 触控细节**：设置 `touch-action`、`user-select`、`-webkit-tap-highlight-color`，禁用双击缩放。
- **耗电**：避免高频 `setInterval` 和常驻动画，夜间模式用 CSS 变量切换，不要整页重渲染。

## 7. 避免事项

- **不要让整本书走 IPC**（base64 或 JSON），大文件用 `book://` 流式读取。
- **不要依赖 content:// URI 长期有效**，导入时必须复制到私有目录。
- **不要用页码当进度**，用 CFI 加百分比。
- **不要自己手写 EPUB 排版引擎或 CFI 实现**，工作量巨大，直接用 foliate-js 或 Readium。
- **不要在阅读页用重型动画库**，翻页动画用 CSS transform，relocate 事件走 ref 或局部订阅。
- **不要把 WebView 的 localStorage 当主存储**，它可能被系统清理，用 SQLite 或 store 插件。
- **不要让前端直连数据库拼 SQL**，业务规则散落在 JS 里，后续迁移和同步都难做，应封装成 Rust 命令。
- **Rust 依赖避开 openssl**，Android 交叉编译很麻烦，用 rustls。
- **MVP 不要一上来支持全格式**，先 EPUB + TXT，其余后加。
- **不要只在模拟器上测**，至少覆盖一台低端机、一台国产 ROM 机型和一台较新的原生系统机型。
- **不要支持带 DRM 的书籍**（Kindle、Adobe ADEPT 等），既不可行也有版权风险。

## 8. 实施路线

**Phase 0：三个 spike（先做，决定方案能不能成立）**

1. Tauri Android + foliate-js，通过 `book://` Range 在真机上打开一本 EPUB，跑通翻页手势，并在低端机上测分页性能。
2. Kotlin 插件：SAF 选书 → 复制到私有目录 → 响应"用本应用打开"（intent-filter）。
3. 在目标最低 WebView 版本的真机上验证 UI 样式（Tailwind 版本选择由此决定）。

**Phase 1（MVP）**：书架、导入（EPUB + TXT）、阅读（主题、字体、目录、书签、进度）、本地存储。

**Phase 2**：批注高亮、书内搜索与全库检索、阅读统计、WebDAV 同步、备份导出。

**Phase 3**：MOBI/AZW3/FB2/CBZ、PDF（PDF.js）、TTS、OPDS 在线书库。

**Phase 4**：低端机性能打磨、无障碍、发布与更新渠道。
